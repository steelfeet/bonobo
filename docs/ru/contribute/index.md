# Участие в проекте

Есть много разных способов, которыми вы можете внести вклад, и не все из них включают написание кода. Не думайте, что вклад без кода имеет меньшую ценность — все вклады очень важны.

* Вы можете внести вклад в документацию.
* Вы можете помочь воспроизвести ошибки и предоставить больше информации в issue.
* Вы можете открывать issue с проблемами, с которыми вы сталкиваетесь.
* Вы можете помочь создать лучший презентационный материал.
* Вы можете рассказать об этом в вашей локальной группе пользователей Python.
* Вы можете улучшить примеры.
* Вы можете улучшить тесты.
* и т.д.

## tl;dr

1. Форкните репозиторий github

```shell
$ git clone https://github.com/python-bonobo/bonobo.git  # измените это, чтобы использовать ваш форк.
$ cd bonobo
$ git remote add upstream https://github.com/python-bonobo/bonobo.git
$ git fetch upstream
$ git checkout upstream/develop -b feature/my_awesome_feature
$ # код, код, код, тест, документация, код, тест ...
$ git commit -m '[тема] .... бла-бла-бла ....'
$ git push origin feature/my_awesome_feature
```

2. Откройте pull request
3. Повторите

## Вклады, связанные с кодом (включая тесты и примеры)

Вклад в bonobo обычно делается следующим образом:

* Обсудите идеи в [трекере issue](https://github.com/python-bonobo/bonobo) или на [Slack](https://bonobo-slack.herokuapp.com/).
* Форкните [репозиторий](https://github.com/python-bonobo).
* Подумайте о том, что произойдёт с существующим пользовательским кодом, если ваш патч будет применён.
* Рано откройте pull request с вашим кодом, чтобы продолжить обсуждение во время написания кода.
* Попробуйте написать простые тесты и несколько строк документации.

Хотя у нас пока нет полного руководства по этой теме, лучший способ — форкнуть репозиторий github и отправлять pull requests.

### Руководящие принципы

* Мы стремимся использовать [семантическое версионирование](http://semver.org/). Это должно быть на 100% верно, как только мы достигнем 1.0, но до этого мы будем ошибаться и учиться. В любом случае, усилия пользователя для каждого нарушения обратной совместимости — настоящая боль, и мы хотим держать это в уме.
* Веха 1.0 имеет одну цель: создать надёжный фундамент, на который мы можем положиться в плане API. Чтобы достичь этого, мы хотим сохранить его как можно более минималистичным, рассматривая только несколько пользовательских инструментов как публичный API.
* Проще говоря, ядро должно оставаться как можно более лёгким.
* Давайте не ссоримся из-за стандартов кодирования. Мы обеспечиваем их с помощью [yapf](https://github.com/google/yapf#yapf), и вызов `make format` должен переформатировать всю кодовую базу для вас. Мы рекомендуем вам запустить его перед созданием pull request, и он будет запущен перед каждым выпуском в любом случае, поэтому мы можем сосредоточиться на вещах, которые имеют ценность, а не на деталях.
* Тесты важны. Одна очевидная причина заключается в том, что мы хотим иметь стабильную и работающую систему, но одна менее очевидная причина заключается в том, что это заставляет делать лучший дизайн, гарантируя, что обязанности хорошо разделены, а область действия каждой функции ясна. Чаще всего "единственный очевидный способ сделать это" станет очевидным, как только вы напишете тесты.
* Документация важна. Это единственный способ, которым люди могут фактически понять, что делает система, и бесполезное программное обеспечение бессмысленно. Одна книга, которую я прочитал давно, говорила, что половина энергии, потраченной на создание чего-то, должна быть посвящена объяснению того, что и почему вы что-то делаете, и это, вероятно, один из лучших советов, которые я читал (хотя, как и любой хороший совет, его легче повторить, чем применить).
